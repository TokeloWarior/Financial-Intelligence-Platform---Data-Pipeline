## 2. Existing pipeline behavior before S3

Before adding AWS S3, the flow was manual:

1. Run synthetic data generation scripts.
2. Scripts create local CSVs in data/synthetic/.
3. Manually run ingestion scripts to insert CSV rows into PostgreSQL raw tables.
4. Manually run validators.
5. Manually run cleaning scripts.
6. Cleaning scripts read raw data from PostgreSQL and write cleaned data into clean schema tables.

The database already has operational schemas/tables such as:

- ops.ingestion_batches
- ops.rejected_records
- ops.data_quality_results

There may be more operational tables added later.

The design goal is that PostgreSQL should store structured relational data and metadata only. It should not be used as file storage for CSVs, logs, reports, model artifacts, or other generated objects.

## 3. Migration decision already clarified

Alembic migration files that have already been applied should not be edited. If more clean tables are needed after 0004_create_clean_tables.py has already been applied, the correct approach is to create a new migration, such as:

alembic revision -m "add more clean tables"
alembic upgrade head

The migration chain should grow forward rather than modifying already-applied history.

## 4. Cloud storage decision

We considered Azure Blob Storage and AWS S3. The final decision was to use AWS S3 instead of Azure.

Reasoning:

- S3 will store synthetic CSV files, raw files, processed files, pipeline logs, reports, and model artifacts.
- PostgreSQL remains responsible for relational text/structured data and pipeline metadata.
- This demonstrates understanding of object storage, retrieval, and cloud-ready data architecture.

## 5. S3 bucket design chosen

Instead of using one bucket with many prefixes, we chose multiple buckets from the start for cleaner architecture, access control, lifecycle rules, separation of concerns, and future deployability.

The bucket strategy is one bucket per storage domain per environment.

Current dev bucket pattern:

- fip-dev-synthetic-data-...
- fip-dev-raw-ingestion-...
- fip-dev-processed-data-...
- fip-dev-pipeline-logs-...
- fip-dev-reports-...
- fip-dev-model-artifacts-...

Actual confirmed synthetic bucket:

The AWS region is:

af-south-1

This is the Africa Cape Town region.

## 9. Reusable S3 client created

A reusable S3 storage client was created at:

pipeline/common/s3_storage.py

It defines a class:

S3StorageClient

The class supports:

- upload_file
- download_file
- get_object_bytes
- get_object_text
- read_csv_as_dataframe
- read_csv_as_records
- list_objects
- object_exists
- get_object_metadata
- build_s3_uri
- clean_env_value

The important part is that it can read a CSV directly from S3 using boto3 get_object and pandas.read_csv(response["Body"]).

This means ingestion scripts can read from S3 without permanently storing CSV files locally.

## 11. Updated automation goal

The main objective is no longer just manually uploading files to S3.

The new objective is to start automating the pipeline.

Desired automated flow:

1. Generate synthetic CSV files.
2. Automatically upload generated CSV files to S3.
3. Ingestion scripts retrieve/read the CSVs from S3.
4. Ingestion inserts records into PostgreSQL raw tables.
5. Pipeline records metadata in operational tables such as ingestion_batches.
6. Validators run and write rejected records/data quality results.
7. Cleaning scripts run and load clean tables.
8. Local CSV files should not remain after ingestion succeeds.

The target behavior is:

S3 = persistent object/file storage
PostgreSQL = relational data + operational metadata
Local filesystem = temporary generation workspace only

## 12. Read from S3 vs download decision

Preference is to read CSV files directly from S3 during ingestion, instead of downloading them permanently.

Preferred pattern:

storage = S3StorageClient()
df = storage.read_csv_as_dataframe(bucket_name, object_key)

Fallback allowed later:

Download temporarily to a temp directory, ingest, then delete immediately.

But the preferred demonstration is direct S3 read because it better shows cloud storage retrieval.

## 14. Important architectural guidance

Please keep scripts separated by responsibility:

generate_customers.py / generate_accounts.py
    Only generate synthetic data.

upload_synthetic_to_s3.py
    Only upload generated files to S3 and return metadata.

ingest_raw_customers.py / ingest_raw_accounts.py
    Only ingest records into PostgreSQL, ideally from S3 input.

run_synthetic_ingestion_flow.py
    Orchestrates the end-to-end pipeline.

Do not make generation scripts responsible for S3 upload unless there is a very strong reason.

Also avoid storing CSV content in PostgreSQL. Store only metadata like:

storage_provider = aws_s3
bucket_name = ...
object_key = ...
s3_uri = s3://bucket/key
record_count = ...
status = ...
